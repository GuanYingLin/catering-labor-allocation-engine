M-System 餐飲人事邊際損益決策系統 — 簡報問答清單（Q&A）

【程式碼與資料工程 (Code / Data Engineering)】
Q1：政府的 PDF 報告每年格式都不一樣，甚至會有文字偏移，你的系統怎麼保證抓對資料？
A1：[切換至 附錄 3] 我們不依賴單純的文字讀取。系統底層實作了 `_cluster_words_by_row` 像素座標群聚演算法，透過設定 `y_tolerance=5.0` pt 容差值，動態鎖定文字方塊的絕對座標來重建表格，完全免疫 PDF 排版漂移的干擾。

Q2：如果店長上傳了錯誤的 POS 報表，或者 PDF 解析漏了幾筆資料，會不會算出錯誤排班讓公司賠錢？
A2：[切換至 附錄 4 左圖 & 附錄 5] 不會，系統具備雙層防禦機制。第一層是在 ETL 寫入前（附錄 4），設有 `len(df) == 24` 的維度斷言，資料有缺漏會直接拋出 RuntimeError 阻斷寫入。第二層是自動化整合測試（附錄 5），執行 6 項斷言測試確保資料庫與視圖完整，全數 Pass 才會允許交付前端。

Q3：如果門市的 Excel 檔沒有放在預期的 data/raw 目錄下，系統是否會崩潰？
A3：[切換至 附錄 4 右圖] 系統不會崩潰。我們在 ETL 管線中實作了 `search_dirs` 白名單動態尋址機制。它不僅掃描 data/raw，還會檢索 Downloads 與 Desktop；一旦找到符合命名的 POS 報表，即透過 shutil.copy2 自動複製歸檔至唯讀的原始目錄中，確保管線不斷鏈。

Q4：SQLite 於多門市同時寫入或查詢時的鎖定問題（Concurrency）如何解決？
A4：目前架構定位為單店微觀營運邊緣運算（Edge Computing）。未來規模化部署至集團總部時，因底層皆採用標準化 SQL 語法，可無痛抽換為 PostgreSQL 以解決多連線寫入的鎖定限制。

【資料庫與架構 (Database & Architecture)】
Q5：這幾份 CSV 筆數不多，為何要建置 SQLite 與分析視圖，而不是直接匯入 Tableau 繪圖？
A5：[切換至 附錄 1] 為了建立單一真實數據源 (SSOT)。官方表格的「年份」（缺 2016/2021 普查年）與「分類維度」顆粒度不一。透過 SQLite 預建 `vw_catering_benchmark_mart` 鎖定顆粒度，可徹底阻絕前端 BI 產生重複加總（Fan-out）的嚴重誤差。

Q6：附錄展示的 SQL 語法以 LEFT JOIN 為主，為何未使用更複雜的巢狀查詢？
A6：[切換至 附錄 2] 這是基於軟體工程的職責分離（Separation of Concerns）原則。百筆基準表由 SQLite 負責跨源時間軸對齊（實測耗時僅 431 μs）；高複雜度的非線性稅制階梯與 R1 解析解，則交由 Python 負責運算。我們避免過度設計，確保系統的輕量化與高維運性。

Q7：為何決策引擎採用 Streamlit，而非 React/Vue 等原生前端框架？
A7：在商業分析情境下，Streamlit 允許我們以純 Python 路徑，將複雜的計量模型與 Altair 互動圖表快速轉化為視覺化網頁，達成概念驗證（POC）與決策邏輯交付的最大效率。

【商業邏輯與決策應用 (Business & Delivery)】
Q8：P.10 提及的 AI 智能排班特助，如何防止幻覺（Hallucination）給出錯誤建議？
A8：我們嚴格執行「運算」與「語意生成」的職責分離。LLM 不參與任何財務算術，所有精確指標（如 478,788 元、-89.4% 稀釋率）皆由 Python 計量引擎算妥後，透過 Function Calling 機制封裝注入 System Prompt。LLM 僅負責轉譯，從架構上根除算術幻覺。

Q9：為何將租金與折舊從變動營業費用中強制分離？未分離的財務偏誤有多大？
A9：依據成本習性，租金與折舊在單店產能內屬固定成本。若不將其自變動費用率中剝離，將導致邊際貢獻率（CM）被人為低估。因為 CM 位於 R1 公式分母，分母低估會產生非線性放大效應，導致 R1 門檻產生 1.75% 以上的高估偏誤，阻礙正確的擴張決策。

Q10：若遭遇颱風天等客流驟減，模型是否會給出錯誤的裁員或減班建議？
A10：系統從兩個維度防範極端干擾。第一是時間尺度隔離：R1 門檻是鎖定 270 個營業日的「長期月均營收（409,584 元）」作為基準，單日突發事件不影響固定編制。第二是分層抽樣：ETL 管線已將數據拆分為月度、平假日與時段三張事實表，在同質日型內評估產能，避免極端離群值扭曲常態排班。

Q11：2026 年後基本工資若再度調漲，模型需如何應對？
A11：我們建立的工資模組（clean_minimum_wage_index）具備時間序列延展性。只需將新標準更新進底層 CSV 資料庫，系統即會自動連動重算最新的法定人事乘數（如目前的 1.20 / 1.11），模型無須重新改寫。
