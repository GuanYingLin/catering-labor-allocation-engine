M-System 餐飲人事邊際損益決策系統 — 簡報問答清單（Q&A）


審查維度,攻擊假說 / 潛在提問,應對策略 / 核心論點
程式碼 (Code),非結構化與容錯治理：政府的 PDF 報告每年格式都不一樣，甚至會有文字偏移，你的系統怎麼保證抓對資料？,"我們不依賴單純的文字讀取。系統底層實作了 `_cluster_words_by_row` 像素座標群聚演算法，透過設定 `y_tolerance=6.0` 容差值，動態鎖定文字方塊的絕對座標來重建表格，完全免疫 PDF 排版漂移的干擾。"
程式碼 (Code),ETL 嚴格防護與資料完整性：如果今天店長上傳了錯誤的 POS 報表，或者 PDF 解析漏了幾筆資料，系統會不會算出錯誤的排班直接讓公司賠錢？,"系統在 ETL 寫入資料庫前，設有嚴格的資料維度斷言檢查。例如，強制檢驗爬取的矩陣是否絕對等於 24 筆（8個調查年度 x 3業別）。只要資料有任何缺漏，程式會在寫入 SQLite 前直接拋出 `RuntimeError` 阻斷執行，絕不讓污染數據進入決策引擎。"
程式碼 (Code),跨資料夾動態尋找機制：如果門市的 Excel 檔沒有放在預期的 `data/raw` 目錄下，系統是否會直接崩潰？,"不會。我們在 ETL 管線中實作了 `search_dirs` 動態尋找機制，不僅會掃描 `data/raw`，還會自動遞迴搜尋使用者的 `Downloads` 與 `Desktop` 目錄，找到後會自動複製一份至唯讀的 `data/raw` 中，確保資料流不會中斷。"
程式碼 (Code),技術選型：為何決策引擎採用 Streamlit，而非 React/Vue 等原生前端框架？,作為商業分析背景，Streamlit 允許以純 Python 路徑將複雜的計量模型與 Altair 互動圖表轉化為網頁，達到概念驗證（POC）交付速度最大化。
程式碼 (Code),防禦斷路機制：若食材與變動費用率過高，導致邊際貢獻率（CM）過低甚至為負，系統如何反應？,底層寫入邊際貢獻率（CM）警戒防禦。當 CM 低於 15% 時，觸發 cm_critical_threshold 斷路保護，直接鎖死 R1 擴編發散計算並拋出結構性倒掛警示，強制要求下調食材成本以進行停損。
程式碼 (Code),效能與併發：SQLite 於多門市同時寫入或查詢時的鎖定問題（Concurrency）如何解決？,目前定位為單店／區域微觀營運邊緣運算（Edge Computing）。未來規模化部署至集團總部時，因底層皆採用標準化 SQL 語法，可無痛抽換為 PostgreSQL 解決多連線寫入鎖定問題。



資料庫與架構 (Database),資料倉儲必要性：這幾份 CSV 筆數不多，為何要建置 SQLite 與檢視表，而不是直接匯入 Tableau 繪圖？,[切換至附錄 3-1] 為了建立單一真實數據源 (SSOT)。多源官方表格的「年份」（缺 2016/2021 普查年）與「分類維度」顆粒度不一。透過 SQLite 預建標準化分析視圖（vw_catering_benchmark_mart）鎖定顆粒度，可阻絕前端 BI 產生重複計算（Fan-out）誤差。
資料庫與架構 (Database),SQL 查詢設計深度：附錄展示的 SQL 語法以 LEFT JOIN 與 View 為主，為何未使用更複雜的巢狀查詢？,[切換至附錄 3-2] 基於職責分離（Separation of Concerns）與避免過度設計。百筆基準表由 SQLite 負責跨源時間軸對齊（耗時僅 431 μs）；高複雜度的解析解則下放至 Python。面對百萬級交易場景，才會在 SQL 層導入 CTE、視窗函數進行優化。
交付 (Delivery),POS 自動化整合：目前為靜態 CSV 載入，未來自動化 API 介接的資料延遲限制為何？,考量排班屬中長期決策，不追求毫秒級實時串流。規劃採用每日批次（Daily Batch）或每班次（Shift-based）結帳後拋轉，以降低系統負載與維運成本。
交付 (Delivery),LLM 介接幻覺：P.11 提及之 AI 特助，如何防止幻覺（Hallucination）給出錯誤排班建議？,"採用檢索增強生成（RAG）與函數呼叫（Function Calling）。AI 不負責數學運算，僅將 Streamlit 引擎吐出的確切數字（如 478,788 元）轉化為自然語意。"
交付 (Delivery),環境建置與溯源：如何確保本地端 Python 依賴套件於終端機無縫部署？,嚴格遵守端到端檔案分層，透過 requirements.txt 鎖定套件版本，確保資料清洗管線與 Streamlit 引擎在異地部署環境的可重現性。
交付 (Delivery),權限管控邊界：門市店長與總部高層的檢視權限與參數修改邊界為何？,系統在 UI 上實作了參數分級。總部鎖定「法定負擔乘數、宏觀折舊率」等總體變數於後端；店長僅具備開放「新增兼職時薪／時數」之微觀變數輸入權限。
交付 (Delivery),視覺化圖表自適應：在不同載具（如店長手機或總部大螢幕）的易讀性？,採用 Altair 響應式圖表，綁定 use_container_width=True，並注入自定義 CSS 高對比樣式，確保跨載具皆能在 5 秒內認知產能定位。
商業 (Business),成本切分依據：為何將租金與折舊從變動營業費用中強制分離？未分離的財務偏誤有多大？,若不分離，等同假設租金會隨營收無上限膨脹，將嚴重低估高營收帶的真實淨利，並導致 R1 門檻產生 1.75% 以上的高估偏誤，阻礙擴張決策。
商業 (Business),法規聯動機制：2026 年後基本工資若再度非對稱調漲，模型需如何應對？,基礎工資模組（clean_minimum_wage_index）具備時間序列擴展性。只需將新標準更新進底層 CSV，系統即自動連動並重算最新的法定人事乘數（目前為 1.20 / 1.11）。
商業 (Business),沉沒成本考量：門市裝潢與初期設備投入，是否應計入 R1 損益兩平門檻？,嚴格遵守個體經濟學邊際原則。沉沒成本不影響「下一次增員」的邊際決策，因此僅計入每月攤提之折舊，不影響邊際貢獻率計算。
商業 (Business),SPLH 極端盲區：若遭遇颱風天客流驟減，模型是否會給出錯誤的裁員建議？,SPLH 屬常態產能指標。系統鎖定 270 日均值進行長期決策；針對短期極端氣候的離群值（Outlier），會於資料進入 Python ETL 階段時透過常態分佈預先濾除。
商業 (Business),決策落地轉化：產出「方案 B（增兼職）」結論後，店長於實務排班表上應如何具體調度？,對照單日時段集中度（尖峰 4 小時佔 60.3%），將新增的兼職工時精準填補於 07:00–09:00 及 11:00–13:00，截斷離峰冗餘工時。
